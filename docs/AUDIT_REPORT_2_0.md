## 1. Executive Summary

A full line-by-line inspection of the existing codebase (`extension/`, `src/`, `public/`, `snap-vanish-chrome-extension.zip`, `package.json`, `vite.config.ts`, `tsconfig.json`, and `src/__tests__/`) revealed two distinct layers of issues:

1. **Legacy Archive (`snap-vanish-chrome-extension.zip`)**: Still contains the broken v1.4.0 prototype where `estimateHands()`, `segmentSelfie()`, `median3()`, and `buildDustScene()` throw runtime exceptions, `extension/content/snap-vanish.css` is missing, and `models/*` is missing.
2. **Current Checked-Out Source (`669444d`)**: Although an earlier pass added basic scaffolding so files do not throw on load, **critical core capabilities remain unimplemented, stubbed, or architecturally incomplete**:
   - **No Real Hand Detection**: `estimateHands()` in `extension/content/snap-vanish.js` merely checks `window.__snapVanishHandEstimator`, which is **never defined anywhere**. `@mediapipe/tasks-vision` is not installed, no `.task` or `.wasm` model assets exist in the repository, and no camera inference loop runs in either the extension or the React app.
   - **Dead Detection & Audio Code in Content Script**: `VanishController` instantiates `this.detector = new SnapDetector(...)`, and defines `class AudioConfirmer`, **but never calls `this.detector.push()` or instantiates/polls `AudioConfirmer` anywhere**.
   - **Coordinate Scale Bug in Gesture Detection**: `SnapGestureDetector` uses millimeter constants (`DEFAULT_TIP_FAR_MM = 45`, `DEFAULT_TIP_NEAR_MM = 12`) directly on `dist3(lm[4], lm[12])`. Real MediaPipe `landmarks` are normalized `[0..1]` and `worldLandmarks` are in **meters** (`0.01`–`0.06` m), meaning raw MediaPipe outputs would never exceed `45` and would fail 100% of real hand snaps without meter-to-millimeter / palm-scale normalization.
   - **Fake Foreground Segmentation & Static Gradient Plate in Content Script**: `segmentSelfie(imageData)` in `extension/content/snap-vanish.js` unpacks `imageData.data` and **never reads a single pixel**, returning a hardcoded static ellipse. `this.plate` is painted as a brown CSS gradient rather than capturing or estimating a real camera background plate.
   - **No Outgoing WebRTC Stream Replacement**: `manifest.json` only injects `content/snap-vanish.js` in Chrome's `ISOLATED` world at `document_idle`. `peerConnections()` checks `window.__snapVanishPeerConnections`, which nothing populates. Consequently, outgoing camera tracks on Google Meet / Teams / Zoom are never replaced via `RTCRtpSender.replaceTrack()`.
   - **Manifest V3 CSP Syntax Bug**: `extension/manifest.json` declares `"script-src 'self' wasm-unsafe-eval; object-src 'self'"` — missing mandatory single quotes around `'wasm-unsafe-eval'`.
   - **Visual Identity & UX Mismatch**: `src/App.tsx` and `src/index.css` still render a cream/beige newspaper marketing landing page (`#f2ede3`) with outdated `v1.4.0` strings in `Sections.tsx`, mixed with generic `#7c3aed` purple/violet dashboard panels, lacking the cohesive deep charcoal/black + warm ember design system, 9-category Settings page, 7-step Guided Calibration, and 8-step Onboarding.
   - **Idle CPU Drain**: `SnapStage.tsx` runs an unconditional `requestAnimationFrame` canvas redraw every 16.6ms forever—even when `status === "idle"` on a static image and even when the browser tab is hidden (`document.hidden`).

## 3. Feature Feasibility & Platform Compatibility Matrix

### 3.1 Video Conferencing Integration Feasibility

Browser security isolates extension content scripts (`ISOLATED` world) from page scripts (`MAIN` world). To genuinely transform an outgoing video call stream in Chrome 121+, an extension must intercept media in the `MAIN` world prior to or during `RTCPeerConnection` track attachment.

| Platform | Integration Mechanism | Outgoing Stream Replacement | Local Self-View / HUD | Honest Classification in Our Build |
|---|---|---|---|---|
| **Google Meet** (`meet.google.com`) | Standard WebRTC `RTCPeerConnection` + `getUserMedia`. `MAIN`-world bridge at `document_start` tracks `RTCRtpSender`s (`kind === "video"`) and swaps track via `sender.replaceTrack(canvasTrack)`, restoring original camera track on return. | Supported via `MAIN`-world `RTCRtpSender.replaceTrack()` + `getUserMedia` stream proxy; falls back to `dom-overlay` if meeting already started without refresh. | Supported (non-intrusive floating status pill + Emergency Restore). | **Implemented (Untested in live Meet call in sandbox — no Chrome/webcam hardware in Linux container)** |
| **Microsoft Teams Web** (`teams.microsoft.com` / `teams.live.com`) | Chromium WebRTC `RTCPeerConnection` in web client. Same `MAIN`-world `RTCRtpSender.replaceTrack()` + `dom-overlay` fallback. Note: Teams may renegotiate video tracks on layout/spotlight changes, so sender set is re-checked dynamically. | Supported via `MAIN`-world `RTCRtpSender.replaceTrack()` with `dom-overlay` fallback. | Supported. | **Implemented (Untested in live Teams call in sandbox)** |
| **Zoom Web Client** (`*.zoom.us`) | Zoom Web Client frequently uses custom **WebAssembly / WebCodecs / OffscreenCanvas** video encoding over WebSockets/WebTransport rather than standard `RTCPeerConnection` video `RTCRtpSender`s. Therefore `RTCRtpSender.replaceTrack()` often has 0 video senders on Zoom Web! However, `getUserMedia` stream wrapping at `document_start` (supplying a pass-through canvas `MediaStream` when live and disintegrating on trigger) + `dom-overlay` fallback + **OBS Virtual Camera workflow** provides a honest, working path. | Experimental via `getUserMedia` stream proxy; **OBS Virtual Camera** recommended for 100% guaranteed Zoom desktop/web compatibility. | Supported. | **Experimental / Partial (Untested in live Zoom call in sandbox)** |
